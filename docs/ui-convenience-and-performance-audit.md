# Hover UI 편의 기능과 성능 개선 검토

2026년 10월 20일 최초 검토. 추가할 편의 기능으로는 **키보드 탐색과 명시적인 고정 기능**, **실패 이유와 재시도 표시**, 분리된 미리보기의 소스 복사와 내부 검색이 있다. 기존 포인터 처리와 캐시 예산은 유지한다.

대상은 VS Code 데스크톱의 native hover와 분리된 hover 창이다. 아래의 최초 감사와 실험은 제품 코드 변경 전에 수행했다. 소스 검사, VS Code 1.142.0의 성능·캐시 테스트, 후보 수집 함수의 Node 실험을 근거로 삼았다. 최초 감사 당시 화면 도구는 시간 초과되었다. 이후 정리와 실제 렌더링 검증 결과는 [성능 기록](performance.md)에 별도로 정리한다.

## 원문 보존을 우선하는 적용 범위

긴 코드의 원문 전체 보기가 이 도구의 목적이며 필수 조건이다. 주석·docstring·전체 구문 강조·마지막 줄 접근과 창 분리·Back 후 복원을 유지한다. 줄 수나 문자 수로 표시를 줄이거나, 뒷부분을 요약·생략·일반 텍스트로 대체하는 최적화는 적용하지 않는다.

이번 정리에서는 후보 검색용 임시 줄 배열만 기존 검색 범위에 맞춰 생성하고, 테스트 실행 파일 선택을 공통화했다. 초기 감사의 후보 수집 및 macOS 테스트 경로 문제는 patch 323에서 정리했다. 표시할 원문이나 후보 검색 범위 자체는 바꾸지 않았다.

이후 0.2.6051의 patch 324에서는 분리창의 실패 이유와 Retry를 구현했다. 기존 제목줄과 VS Code 토큰을 사용하며, 실패·재시도 중에는 본문과 스크롤을 유지한다. 요청 ID가 지난 응답과 commit은 무시한다. 제목줄의 표시 순서를 보정하고 긴 이름에는 전체 제목 툴팁을 제공한다. 최종 기능·화면 검증은 [성능 기록](performance.md)에 정리한다.

0.2.6052의 patch 325에서는 명시적인 Pin 버튼과 명령 팔레트의 고정 명령을 구현했다. 코드와 분리된 기존 호버 스크롤 내부 도구줄을 사용하며, 전체 원문과 native 크기 조절을 보존한다. 키보드로 고정창을 닫으면 연결된 편집기로 포커스를 돌린다. 자세한 계약은 [UI 구조](hover-ui-structure.md)의 Explicit Pin 절에 있다.

0.2.6053의 patch 326에서는 고정창의 Symbols 버튼에서 VS Code 기본 Quick Pick을 열어 키보드로 타입을 선택한다. 검색은 후보 접두 범위를 넘어 원문 전체에 도달하며, 목록만 200개로 제한한다. Pin → Shift+Tab → Enter → 검색 → 정의 선택 → Back → 닫기의 키보드 경로를 제공한다. 오래된 검색과 선택은 페이지·창·요청 식별자로 거부한다. 원문과 토큰 DOM을 검색을 위해 변경하지 않는다.

탐색 기록의 용량 제한은 Back 동작을 줄일 수 있으므로 보류한다. 기존 탐색을 보존하는 복원 정책이 검증되기 전에는 기록을 임의로 자르지 않는다. 소스 복사·본문 검색과 창 한도 정책은 이후 후보로 남긴다.

## 현재 유지할 동작

- VS Code가 native hover의 배치, 테마, 스크롤, 크기 조절을 소유한다. 자동 크기는 680px × 48vh 범위이며 사용자가 native sash를 끌면 확장할 수 있다.
- 클릭 고정, 드래그로 창 분리, 창별 독립 탐색과 Back, 원본 파일의 정확한 줄 열기가 이미 구현되어 있다. 파일 링크에는 Enter 처리도 있다.
- 소스의 주석, docstring, 마지막 줄과 전체 구문 강조를 보존한다. 후보 탐색이나 캐시를 최적화할 때 표시 내용을 줄이지 않는다. [UI 계약](hover-ui-structure.md)을 유지한다.
- 정의 캐시와 위치별 캐시는 각각 추정 payload 4 MiB 예산과 TTL을 갖는다. 진단 observer와 listener는 필요할 때만 설치된다.

## 코드 감사 결과

점수는 코드와 아래의 제한된 실행 검사에 대한 잠정 평가다. 대비, 테마 전환, 좁은 창의 실제 배치, 보조 기술 사용성을 인증하는 점수는 아니다.

| 영역 | 점수 | 근거와 남은 확인 |
| --- | ---: | --- |
| 접근성 | 1/4 | 타입 링크가 포커스 불가능한 span이며 분리 동작이 드래그에 의존한다. Back과 닫기는 이름을 가진 button이다. |
| 성능 | 3/4 | 포인터·observer·캐시 회귀 5개 통과. native 기록은 상한이 없고, 큰 입력의 후보 수집에는 불필요한 전체 줄 분할이 남아 있다. |
| 좁은 데스크톱 창 대응 | 2/4 | 분리창에 viewport 8px 여백과 크기 제한이 있다. 실제 좁은 창, 확대, 긴 경로 배치는 확인하지 못했다. |
| 테마 | 2/4 | VS Code 토큰을 사용한다. 분리 시 복사한 계산된 색상이 테마 전환에도 맞는지는 추가 검증이 필요하다. |
| 구현 일관성 | 3/4 | native 중심 설계를 유지한다. 자동 detector 결과는 0건이며, 테스트 실행 파일 경로 호환성 문제는 재현되었다. |
| 합계 | 11/20 | 코드 기준 개선 필요. 렌더링 품질과 제품 출시 준비 상태에 대한 판정은 보류한다. |

구현 일관성은 코드 범위에서 통과한다. 기존 VS Code 컴포넌트와 토큰을 확장하는 구조이며 새로운 시각 체계가 필요하지 않다. 자동 detector의 0건은 JS 문자열 안의 사용자 경험 결함이 없다는 보장이 아니다.

최초 확인된 항목은 P0 0건, P1 1건, P2 5건, P3 0건이다. 아래의 기능 제안과 추가 검증 항목은 결함 수에 포함하지 않는다. 점수와 문제 목록은 정리 전 상태를 나타낸다.

### P1 타입 탐색과 창 분리에 키보드 경로가 없다 — patch 325·326에 반영

위치: [renderer-patch.ts](../src/renderer-patch.ts)의 `irWrapTextNodeWord` 약 10301행, `irWrapDetachedPreviewLinks` 약 5678행, 전체 wrap 경로 약 12907행, `irTypeLinkClick` 약 10920행.

각 경로가 만드는 `.ir-type-link`는 `data-type`만 가진 span이다. Tab 포커스, 역할, Enter 처리가 없고 클릭 처리만 연결되어 있다. 큰 블록은 포인터 위치에서 링크를 만드는 방식이므로 span에 tabindex만 추가해도 전체 키보드 탐색이 해결되지는 않는다. 분리창 생성도 포인터 드래그가 진입점이다. 마우스를 사용할 수 없는 사용자가 핵심 작업을 수행하기 어렵다. [WCAG 2.1.1 키보드 조작](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) 및 [2.5.7 드래그 대안](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) 관점의 검토 대상이다.

명시적인 고정 버튼과 명령은 patch 325에, 큰 정의에서 DOM 링크 수를 늘리지 않는 심볼 선택 목록은 patch 326에 반영했다. 포인터용 span의 개별 Tab 순회 대신 기본 Quick Pick을 사용한다. 닫기 후 원래 editor로 포커스를 복원한다. 소스 복사와 본문 검색은 별도의 미구현 후보이며 심볼 검색에 포함되지 않는다.

### P2 분리창 탐색 실패가 화면에 남지 않는다 — patch 324에 반영

위치: [renderer-patch.ts](../src/renderer-patch.ts)의 `irFailDetachedPreview` 약 5836행, `irUpdateDetachedHoverChrome` 약 5662행.

로딩 제목은 있으나, 실패 시 busy와 pending 이름을 지운 뒤 제목을 복구하고 진단 로그만 기록한다. 15초 timeout, 연결 부재, 해석 실패를 사용자가 구분하기 어렵다. 기존 내용을 유지하면서 실패 이유와 재시도를 표시하고, 상태 변화는 접근 가능한 live region으로 알린다. `impeccable harden`과 `impeccable clarify` 대상으로 삼는다.

### P2 native 탐색 기록의 보관량에 상한이 없다

위치: [extension.ts](../src/extension.ts)의 native `previewHistory.push` 약 11305행, [preview-history.ts](../src/preview-history.ts)의 `PreviewState`와 `previewHistory`.

native 기록은 전체 Markdown을 가진 상태를 계속 push한다. 세션 초기화 시 정리는 있지만 건수나 payload 상한이 없다. 반면 renderer와 분리창 기록에는 20단계 제한이 있다. 캐시의 4 MiB 제한은 이 기록에 적용되지 않는다. 긴 정의를 연속 탐색하면 별도 보관량이 커질 수 있다. 실제 RSS 증가량은 측정하지 않았다.

각 프로세스의 기록 정책을 일치시키고, 오래된 페이지는 위치·문서 버전·스크롤 정보로 보관한 뒤 필요할 때 전체 내용을 재구성하는 방식을 검토한다. renderer와 extension에서 기록을 따로 잘라 Back 상태가 어긋나지 않게 해야 한다. `impeccable optimize` 대상으로 삼는다.

### P2 후보 수집의 전체 줄 분할이 탐색 제한보다 먼저 실행된다 — patch 323에 반영

위치: [renderer-patch.ts](../src/renderer-patch.ts)의 `irCollectTypeShapedCandidates` 약 10460행. 호출자는 큰 입력의 탐색 범위를 50,000자·900줄로 제한하지만, 함수는 먼저 원문 전체를 `split`한다.

제한 범위까지만 줄을 읽는 실험은 큰 입력에서 이 비용을 줄였다. 작은 입력에서는 실험 구현이 더 느렸으므로 모든 크기에 일괄 적용할 근거는 없다. 큰 입력에만 적용하고 후보 동일성, CRLF, 제한 경계, 한 줄이 매우 긴 소스를 검증한다. 표시할 원문과 구문 강조는 그대로 유지한다. `impeccable optimize` 대상으로 삼는다.

### P2 창 보관 한도를 넘으면 가장 오래된 창이 조용히 닫힌다

위치: [renderer-patch.ts](../src/renderer-patch.ts)의 `IR_DETACHED_HOVER_MAX=12` 약 5032행과 창 생성 후 `window-cap` 제거 약 5599행.

13번째 창을 만들면 가장 오래된 창을 제거한다. 해당 코드에는 제거 안내나 복원 경로가 없다. 여러 정의를 비교하던 사용자는 이전 창을 잃은 이유를 알기 어렵다. 한도를 알리고 닫을 창을 선택하거나, 닫힌 창의 위치 정보를 복구할 수 있게 한다. `impeccable harden` 대상으로 삼는다.

### P2 기본 테스트 실행기가 현재 macOS 실행 파일명을 찾지 못한다 — patch 323에 반영

위치: [runTest.ts](../src/test/runTest.ts)의 `runTests` 호출과 `@vscode/test-electron` 2.5.2.

현재 기본 실행은 VS Code 1.142.0을 다운로드한 뒤 `Contents/MacOS/Electron`을 찾다가 ENOENT로 종료했다. 다운로드된 앱의 실제 실행 파일과 `CFBundleExecutable`은 `Code`다. 임시 래퍼에서 `vscodeExecutablePath`에 실제 경로를 전달하자 동일한 테스트 5개가 통과했다.

실행 파일 경로를 명시할 수 있는 옵션과 검증된 버전을 고정하는 옵션을 테스트 진입점에 추가한다. 이 항목은 UI 결함보다 검증 재현성에 관한 문제이며, 제품 시작 실패로 해석하면 안 된다.

## 성능 측정

VS Code 1.142.0, macOS ARM64, Python fixture, unbundled 개발 빌드에서 측정했다. 원본 결과는 [renderer-performance.json](../reports/ui-audit-2026-10-20/renderer-performance.json)에 있다.

| 작업 | 현재 결과 |
| --- | ---: |
| hover 밖 포인터 이동 1,000쌍 | 10.6ms |
| 위 작업의 document query 및 geometry read | 각각 0회 |
| editor paint 40배치의 DOM query 및 geometry read | 2회 및 0회 |
| dispose한 editor 64개 중 보관된 참조 | 0개 |
| 성능·캐시 회귀 | 5개 통과 |

이 결과는 특정 작업의 비용이며 전체 CPU, GPU, RSS, 첫 hover 지연을 뜻하지 않는다. 기존 listener 정리와 캐시 예산 검사를 다시 통과했다는 근거로 사용한다.

후보 수집 실험은 **현재 함수와 범위까지만 줄을 읽는 대안**을 Node VM에서 비교했다. 7개 표본의 중앙값이며 표본마다 10회 호출했다. 입력별 후보 목록과 빈 문자열·CRLF·긴 한 줄·줄 제한을 포함한 총 8개 사례의 결과가 일치했다. 제품 코드는 변경하지 않았다.

| 입력 줄 수 | 문자 수 | 현재 함수 | 실험 대안 |
| --- | ---: | ---: | ---: |
| 1,002 | 63,040 | 0.070ms | 0.118ms |
| 10,002 | 630,040 | 0.197ms | 0.114ms |
| 100,002 | 6,300,040 | 2.417ms | 0.127ms |

Node 함수 단위 실험으로 Electron의 체감 지연 개선을 입증하지는 않는다. [실험 코드](../reports/ui-audit-2026-10-20/candidate-benchmark.cjs)와 [원본 결과](../reports/ui-audit-2026-10-20/candidate-benchmark.json)를 함께 보관한다. `npm run compile` 후 `node reports/ui-audit-2026-10-20/candidate-benchmark.cjs`로 재측정할 수 있다.

## 검증 결과와 다음 구현의 통과 기준

`npm run compile`은 통과했다. `renderer-performance.test.js`의 3개 테스트와 `preview-cache-budget.test.js`의 2개 테스트는 임시 실행 파일 경로 보정을 통해 exit code 0으로 완료했다. 캐시 검사에는 LRU, 초과 payload 보관 제외, 닫힌 정의 참조 정리, 조회 없는 TTL 만료가 포함된다. Impeccable detector는 0건을 반환했다. 접근성과 상호작용 코드는 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)를 참고해 검토했다.

화면 도구는 현재 editor와 격리된 테스트 앱 모두 시간 초과되었다. 이번 검토에서 desktop·좁은 창·태블릿·모바일 크기의 화면, 일반 클릭·Tab·Enter·Escape 입력, 밝은 테마·어두운 테마·고대비, console/network 상태는 시각 또는 대화형 QA로 확인하지 못했다. 데스크톱 확장이므로 다음 검증은 1440 × 900과 1024 × 768의 실제 VS Code 창을 우선한다. 모바일 지원을 전제로 하지 않는다.

구현 순서는 키보드와 고정 기능, 실패 피드백, 기록 보관 정책, 큰 입력의 후보 수집 순으로 권한다. 이후 복사와 검색을 추가하고 `impeccable polish`로 마무리한다. 각 단계는 독립적으로 진행할 수 있다.

- 키보드로 고정·타입 선택·Back·닫기를 수행하고 원래 editor로 포커스가 돌아온다. 큰 정의에서도 링크 수만큼 Tab을 반복하지 않는다.
- 미해석·연결 끊김·timeout·재시도·닫힌 창의 늦은 응답을 확인한다. 진행 중인 창만 비활성화하고 다른 창은 계속 사용할 수 있다.
- 12개 창과 한도 초과를 확인한다. 기존 창을 잃을 때 이유와 복구 경로를 알 수 있다.
- 긴 탐색에서도 보관량이 합의한 예산 안에 머문다. native·분리창의 탐색 경로와 스크롤 복원이 서로 섞이지 않는다.
- 10,000줄 이상의 정의에서 주석, 전체 구문 강조, 마지막 줄, 원본 파일 열기와 복사 결과를 확인한다. 후보 탐색 최적화가 표시 내용을 바꾸지 않는다.
- 실제 창 두 크기에서 긴 제목·경로·조밀한 내용·resize·확대·테마 전환을 확인하고, 기능 검사와 별도로 화면을 검토한다.
- 수정 후 기존 startup·resize·forward/Back·분리창 격리·파일 링크·전체 내용 테스트와 영향을 받은 성능 검사를 실행한다. UI 감사도 다시 수행한다.
